# 踩坑与恢复经验

以下来自本机安装后检查和 2026-10-10 的显示排错记录。每项分别说明现象和能得出的结论，不把推测写成修复方案。

## 1. RTX 3060 方案不是只靠 EFI

**现象与背景：** 显卡使用 NullMoth，涉及四个系统 kext、Metal 插件、Vulkan 后端和 GSP 固件。

**经验：** EFI 只是启动配置的一部分。升级、卸载和回滚要考虑 `/Library/Extensions`、`/Library/GPUBundles`、`/Users/Shared/nvfw` 和 Auxiliary Kernel Collection。不要同时从 EFI 注入相同显卡 kext。

安装完成后需要重启，注销不能加载新的内核驱动。首次授权扩展也应按作者版本说明操作。

## 2. 显示器支持高刷不等于驱动可稳定输出

**早期记录：** DP 连接 Mi Monitor，EDID 三个块校验通过，包含 2560×1440 的约 60、100、120、144Hz 时序，但显示范围检查 `fbRange_a` 拒绝部分高刷新率模式。

**结论：** 高刷时序已被读取，不等于模式可用，也不能仅凭 EDID 推断 DP 带宽或根因。

**处理：** 使用原生分辨率约 60Hz 作为排错基线，保存日志，等待经过验证的驱动修复；不要凭猜测覆盖 EDID 或反复切换高刷。

## 3. 165Hz：提交日志成功，仍然闪屏和黑屏

在 NullMoth 1.6.0 下选择 165Hz 后，用户报告闪屏随后黑屏。日志记录过 `2560x1440 @164999mHz` 的 COMMIT，稍后又提交约 59.95Hz，但日志不能证明画面已恢复。

排错中还看到 `surfvram dirty` 与异步 flip 拒绝的线索，尚不能确定它们是根因。

**经验：** `COMMIT` 成功、接口返回成功、菜单出现某档刷新率，都不能取代肉眼可用性、持续输出和稳定性测试。

## 4. 144Hz：关闭 direct flip 的实验失败

**实验目的：** 临时将 `debug.nvaccel_iop_flip` 从 `1` 改为 `0`，尝试判断高刷故障是否与 direct VRAM flip 有关。实验安排了 15 秒后请求约 60Hz，以及缺少画面恢复确认时的看门狗。

**实际结果：** 用户看到鼠标拖影、窗口残影，最终桌面冻结。程序对 144Hz 和恢复 60Hz 的请求都返回 `0`；看门狗恢复了 `flip=1` 并重启 WindowServer，桌面仍不可用，用户最终强制重启。

**日志边界：** 捕获到 144Hz 的 `setDisplayMode`，但没有相应的 `switchMode COMMIT`。不能确定硬件时序是否真正切到 144Hz，也不能声称程序请求 60Hz 后显示已恢复。

**经验：** 这个尝试没有修复问题。原测试脚本已经禁用，公开包不提供这个高刷实验脚本。不要照抄 flip sysctl 参数作为所谓优化。

## 5. 自动恢复只能算措施，不能当保证

这次实验表明，恢复参数、请求低刷新率、重启 WindowServer 仍可能无法救回画面。F 型号 CPU 没有备用核显路径。

**经验：** 保存工作、准备恢复 U 盘和可启动备份，比“有看门狗”更基础。强制重启是这次故障中用户实际采用的恢复动作，不应作为正常测试流程。重启后只读检查确认回到 2K、约 60Hz。

## 6. 显卡卸载入口不等于可靠回滚

本机有旧的 “Remove NVIDIA driver” 菜单失效记录。作者 1.6.0 的发布说明也提到某些主板上 NVRAM 删除请求残留、导致登录后驱动被移除的问题，但不能据此认定本机旧问题就是同一个原因。

本机另行准备了离线备份恢复脚本，脚本依赖特定系统构建、分区和备份目录；静态检查完成，完整恢复环境执行未验证。

**公开处理：** 禁用原 EFI 中的卸载工具入口，不发布带有本机卷 UUID 的恢复脚本。建议使用自己安装版本对应的作者恢复方案，并独立验证救援介质。

## 7. 备份必须覆盖 EFI 和当前系统驱动

Time Machine 有备份记录，但本机曾调整系统时间，不能只凭目录日期判断是否覆盖了最新驱动。Time Machine 也不能代替 EFI 分区的单独备份。

**经验：** 在升级前保存 EFI、驱动、插件、固件、AuxKC 和系统构建号，校验备份可读性。旧内核缓存不可直接跨 macOS 构建恢复。不要把“已下载新版本”写成“已验证升级成功”。

## 8. USB 默认映射占满端口，不代表 USB 3.x 可用

安装后 IORegistry 记录为 15 个 `AppleUSB20XHCIPort`、0 个 `AppleUSB30XHCIPort`。现状与默认映射占满 15 端口限制相符，但尚未逐口实测，不能直接断言所有插口的实际速率。

**经验：** 前后置插口使用 USB 2.0 与 USB 3.x 设备逐一测试；Type-C 测两个方向，保留内部蓝牙端口。最终映射应由实测决定，不要长期依赖 `XhciPortLimit` 绕过限制。

## 9. Wi-Fi 看起来是 Ethernet，不一定是异常

本机使用 `itlwm` 2.3.0 和 HeliPort 1.5.0，安装后检查为 `en0 active`，有默认路由。itlwm 在系统里显示为 Ethernet 属于该实现的正常表现。

**经验：** 使用 HeliPort 管理连接；不要据此宣称 AirDrop、接力、蓝牙配对或睡眠后无线恢复已经正常，这些尚未验证。

## 10. 未确认的问题应继续保留为未确认

- 注销闪屏原因未定位。
- 曾见 shutdown stall 采样，不能直接归因于显卡。
- “Metal Supported” 不代表硬件视频编码、游戏或专业软件已通过测试。
- 上游 issue [#66](https://github.com/nullmoth/nvidia-macos-driver/issues/66) 的报告者提过切到 sRGB 色彩配置解决其高刷问题；该方法未在本机验证。
- 上游 issue [#73](https://github.com/nullmoth/nvidia-macos-driver/issues/73) 有刷新率切换后窗口残影的报告，但不同显卡上的相似现象不能证明根因相同。
- 本地查看的 1.7.0 发布说明没有明确声称修复本机的刷新率切换问题；这不是对后续所有版本的判断。

如需向作者报告，应提供所用包版本、macOS 构建、显卡型号、接口、模式切换前后状态和脱敏日志。本仓库没有上传原始个人系统日志，也没有自动向作者发送报告。
